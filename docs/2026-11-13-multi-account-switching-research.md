# Umeet 多账号记忆与一键切换：调研与建议

日期：2026-11-13。状态：调研、本地测试账号配置及多账号记忆／一键切换已实施，详见同目录验收记录。

## 1. 已明确的目标

- 浏览器记住已登录的账号；切到其他账号后，原账号仍在选择列表中。
- 有效登录状态下点击账号即可切换；失效时只要求该账号重新登录。
- 同一浏览器最多保存 **5 个账号，包含当前账号**；同一账号重复登录不占新名额。
- 用户已选择：**同一浏览器的 Umeet 标签页统一切换**。
- 测试角色只配置在本机隔离测试库，不配置正式站点权限。
- 前四个位置供管理员、版主、助手、普通用户使用，第五个普通用户 B 用于检查他人数据隔离。

## 2. 公开产品与实现原则

Google 官方说明：可以同时登录多个账号，从头像菜单添加和选择账号，无须先退出再登录。这证明产品交互模式适合本需求；官方帮助页并未披露它完整的内部会话存储方案，不能把下文设计称作 Google 的具体实现。[Google Account Help](https://support.google.com/accounts/answer/1721977)

Clerk 的多会话文档把“列出已登录会话、选择当前会话、添加账号、退出一个、退出所有”明确分开。这是本功能需要覆盖的完整流程，而不是只画一个账号下拉框。[Clerk 多会话流程](https://clerk.com/docs/guides/development/custom-flows/authentication/multi-session-applications)

会话标识不应存入 JavaScript 可读的 localStorage；HttpOnly Cookie 能限制脚本读取。会话撤销与过期由服务端执行，身份或权限变化需要正确更新会话。以下方案据此提出，属于面向 Umeet 的工程建议。[OWASP HTML5 Security](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html#local-storage)、[OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

## 3. 现有代码意味着什么

| 当前实现 | 对新功能的影响 |
| --- | --- |
| `DemoAuthDialog.tsx` 中“切换账号”打开密码登录框，成功后整页刷新 | 目前没有已登录账号列表，也没有恢复原账号的入口 |
| `session-cookie.ts` 只写一枚 `umeet_session` HttpOnly Cookie | 登录 B 会覆盖浏览器当前的 A 凭证；服务端仍可能保留 A 的有效会话 |
| `sessions` 保存随机令牌的 SHA-256 摘要、有效期、设备和验证时间 | 已具备随机会话与服务端校验基础，无须迁移到另一套认证平台 |
| 成员登录当前期限为 30 天，退出会删除对应会话 | 可以沿用这一上限，但切换不能无限续期，也不能复活已撤销的登录 |
| `issue()` 会把 `authenticated_at` 设为当前时间 | 不能原样拿它实现快捷切换；切换不是新的密码／验证码验证 |
| 管理权限由 `moderationAccess()` 动态计算 | 账号列表可展示角色提示，实际授权仍必须实时计算 |
| Wiki 写操作已有账号绑定检查，其他旧业务未全部统一接入 | 全局切换时要把防串号校验覆盖到发帖、私信、设置、管理操作等写入 |

这些结论来自本项目代码核对，不是对外部产品内部机制的推测。

## 4. 方案比较

| 方案 | 优点 | 取舍 |
| --- | --- | --- |
| 只记住用户名，依靠密码管理器填写 | 修改最少 | 仍需要重新认证，不满足有效会话下一键切回的目标 |
| 每个账号一个受保护的 HttpOnly 凭证 Cookie | 可利用现有会话，方案直接 | 多凭证更新、设备注销、并发添加及统一名额管理较分散，需要另做一致性设计 |
| **服务端管理本浏览器的账号集合与登录授权，浏览器持有受保护的设备凭证和当前会话** | 五账号上限、撤销、退出和跨标签页同步可统一处理；凭证不交给前端脚本 | 要改会话层与注销逻辑，不能仅修改登录弹窗；推荐采用 |

不采用把密码或多个长期登录 token 写入 localStorage／普通 JSON Cookie 的做法。当前 NestJS／MySQL 认证可继续使用，没有必要仅为这个功能引入 Clerk 或重新接入第三方身份系统。

## 5. 推荐的数据与认证结构

建议新增两个对象，命名为实现建议：

- `browser_login_sets`：这个浏览器的已登录账号集合。保存设备凭证摘要、当前账号、集合版本与过期状态。
- `browser_remembered_logins`：最多五条经真实登录验证的账号授权。保存账号、原始认证时间、绝对到期时间、撤销状态及稳定身份，不保存密码或可直接重放的明文会话 token。

现有 `sessions` 关联相应的记忆登录授权。浏览器仅通过 HttpOnly Cookie 持有设备集合的随机凭证与当前访问会话，页面收到的是昵称、头像、角色提示、状态和不具备认证能力的选择标识。

一次点击切换的服务端事务：

1. 验证设备集合凭证；确认目标账号确实属于此集合。
2. 检查目标记忆登录授权尚未过期、撤销或被封禁，重新查询实际权限。
3. 锁定集合版本，切换当前账号，生成／轮换当前访问会话，使旧的活动访问凭证失效。
4. 新访问会话受原记忆授权期限约束；不把过期时间自动重设为“再过 30 天”，也不把原始认证时间重设为“现在”。
5. 返回新的受保护 Cookie 和当前账号摘要；所有标签页清理旧账号界面状态并刷新。

原账号保留的是服务端认可的“此设备已验证登录”授权，不能因为数据库只保存旧 token 摘要，就假设服务器可以把原明文 token 取回来。重新签发访问会话的依据是有效的设备凭证与目标登录授权。

需要同时调整的撤销路径：当前退出、退出本浏览器所有账号、移除本设备账号、密码修改／找回、远程设备注销、账号停用与删除。不能只删除旧 `sessions` 行却留下可以继续签发新会话的记忆授权。敏感操作现有的二次验证要求继续有效。

## 6. 建议交互

点击头像或“切换账号”后，直接显示账号选择器：

```text
切换账号                         已保存 5/5

测试管理员      umeet_test_admin       当前账号
物理学版主      umeet_test_mod         可切换
物理学助手      umeet_test_helper      可切换
普通用户 A      umeet_test_user        可切换
普通用户 B      umeet_test_user_b      可切换

管理本设备账号
添加其他账号（已满时提示先移除一个）
退出当前账号
退出本浏览器所有账号
```

- 第一次添加账号正常验证密码／验证码；以后有效会话下点行即切换，不再重复出现密码表单。
- 当前账号明确标记，点击它不重复刷新；其他账号显示头像、名称、角色范围与登录状态。
- 添加第 6 个账号时明确让用户选择移除哪一个，不能默默淘汰原账号。上限校验放在服务端事务中，处理两个标签页同时添加的情况。
- 已过期账号显示“需要重新登录”，保留可识别的条目，不伪装成可直接切换。
- “移除本设备账号”不删除用户本身，不清除其私人草稿、帖子或其他设备的账号。
- 退出当前账号后显示选择器或公开首页，不自动把用户切成另一个高权限账号。
- 从管理员页切到普通用户后进入其有权限的页面，不把他留在失效的管理员详情中。

## 7. 全标签页同步与数据隔离

用户选择的是同浏览器统一身份，因此保留同域共享的当前会话 Cookie，并使用 BroadcastChannel 或仅携带非秘密通知的 storage 事件同步切换。这里的事件不是认证依据，服务端 Cookie 和授权状态才是。

切换前处理未保存内容；在未保存草稿或待完成请求存在时，不直接覆盖当前账号。提交切换后，停止旧请求、清空旧账号缓存／私信／通知／管理数据，各标签页重新获取当前账号。

所有涉及账号的写请求绑定预期账号与集合版本。旧标签页误把 A 的操作配上 B 的新 Cookie 时，后端返回“账号已切换，请刷新”，不能把操作写到 B。慢请求完成后，也不能把 A 的响应填进 B 的界面。该规则要覆盖旧社区业务，不能只保护 Wiki。

如果某个标签页没有收到广播，服务端版本检查仍会阻止串号；标签页重新获得焦点时再核对当前账号。更复杂的“每个标签页独立身份”不在本次选定范围内。

## 8. 已完成的本地角色账号

五个账号已经创建在 `umeet_rebuild_test_knowledgebrowser`，没有授予正式账号权限，也没有改动浏览器当前 Cookie。

| 角色 | 用户名 | 实际授权 |
| --- | --- | --- |
| 管理员 | `umeet_test_admin` | 平台 `admin`，不是站点所有者 `owner` |
| 版主 | `umeet_test_mod` | 物理学版块的实际版主，含该版块团队管理权限 |
| 助手 | `umeet_test_helper` | 物理学版主团队的实际助手，委派举报、内容与 Wiki 维护权限，无团队／人员管理权限 |
| 普通用户 A | `umeet_test_user` | 无管理权限 |
| 普通用户 B | `umeet_test_user_b` | 无管理权限，用于测试其他人的内容与私人数据隔离 |

按已确认的 Wiki 规则，具备 Wiki 维护权限的版主／助手可以处理全站共享正文；目录与路线仍限其获授权社区。快捷账号按钮将来只选择真实账号，不提升权限，也不把同一账号伪装成四种角色。

密码分别随机生成，保存在被 Git 忽略的 `rebuild/.runtime/local-role-accounts.md`；没有写入版本化文档或前端代码。配置工具为 `rebuild/scripts/setup-local-role-accounts.ts`，从 `rebuild/` 执行 `npm run accounts:local` 可重建或核验这组自有测试账号，不会重置整个数据库。若原有同名账号不归该工具所有，工具会拒绝覆盖。

配置时已校验：五个账号可真实登录当前本机 API；管理员／版主／助手的实际权限和团队关系正确；助手不能跨版块管理，也没有团队／人员管理权；两个普通用户没有管理权限。脚本不把这些账号直接装进尚未实现的切换列表。

注意：现有 `fixture:knowledge` 和 Wiki 浏览器测试会重建该隔离样例库，之后再运行 `accounts:local` 即可恢复角色账号。

## 9. 后续实施与验收

建议按“会话与记忆授权 → 添加／切换／退出 API → 账号选择器 → 全标签页与写请求隔离 → 五角色回归”的顺序实现；作为同一功能完成后开放。

必测：A→B→A 无需重输有效凭证；重启浏览器仍可识别账号；最多五个且重复账号不重复计数；第六个、并发添加、会话过期、退出单个／全部、改密与远程注销、目标账号封禁；切换不重置二次验证时间；多标签页和慢请求不串号；版主／助手不能借切换获得其他权限；未保存内容先处理；普通用户不能看到上一个管理员的页面缓存。

本报告没有声称多账号功能已经可用；当前完成的是调研、建议与真实本地测试账号准备。
