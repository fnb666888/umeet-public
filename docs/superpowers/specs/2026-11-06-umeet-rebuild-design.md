## 1. 产品目标与背景

建立一个面向所有人的主题社区平台。校园是重点内容场景，但用户身份和知识范围不限于学校。用户能够发现和加入社区、交流与互助、分享资源，并把持续有用的知识积累为可共同编辑的百科词条。

首页采用类似 Reddit 的社区导航与信息流结构；本设计只借鉴其社区组织和浏览方式，不要求复刻其品牌、样式或全部机制。原项目的 UI 和架构不作为新系统的基础。

成功的产品体验是：访客能直接找到内容，登录用户能参与交流与共建；每个社区既有不断更新的讨论，也有可持续纠错的 Wiki。资源、帖子、词条之间可以相互引用。

参考文件 `D:/下载/index.html` 是参考材料，其中标注的“已确认”、架构建议、数据、规则和论断均不自动成为本项目需求。本文以本次对话中的选择为依据。

## 3. 目标、非目标与失败条件

### 目标

- 建立六个默认社区，并让新主题社区按相同基本结构运行。
- 用统一账号、权限、搜索和审核连接两端，避免同一内容两套维护。
- 支持真实的多人 Wiki 共建：版本、并发修改检查、差异、回滚、引用均有明确行为。
- 保留不同内容的必要结构：二手价格、问答采纳、活动报名、资源文件等不是仅靠帖子标题模拟。
- 新系统可独立构建、运行、部署和备份；旧项目可独立查阅与恢复。

### 首版非目标

- 站内一对一私信、群聊、支付、交易订单与担保流程。
- 将知识库改成必须顺序阅读的多级手册。
- 把多个社区的同名词条自动合并为全站共享条目。
- 沿用旧项目的架构、迁移旧数据或用自动生成的空壳替代已承诺的首版功能。
- 额外扩展原生 App、积分商城或 AI 问答产品。

### 失败条件

- 公开内容必须登录才可阅读，或者网站和小程序的数据不一致。
- 用户只能投稿，不能直接共同修改 Wiki；历史丢失或回滚直接抹掉旧版本。
- 知识编辑彼此静默覆盖，或内容成为版本不可追踪的普通帖子。
- 开发过程中覆盖旧部署、旧文件、旧数据库或旧上传文件。
- 把开发者建议或待开通的第三方能力表述为用户已确认或已上线。

## 4. 整体路线比较与选择

| 路线 | 优点 | 代价 | 结果 |
| --- | --- | --- | --- |
| 双端分别定制、共用后端 | 可分别处理网站的阅读编辑体验和小程序的移动交互；业务规则一致 | 两套界面需要分别开发和验证 | 用户已选择 |
| 跨端统一页面开发 | 可复用更多界面代码 | 编辑器和平台交互仍需单独适配 | 未选择 |
| 整合现成论坛与 Wiki | 可利用现成系统能力 | 需要协调账号、权限、审核、搜索和双端体验 | 未选择 |

选择理由：独立社区 Wiki、双编辑模式、各类结构化帖子和可选匿名身份需要统一业务模型。分别定制双端能让这些模型按设备特点呈现。

具体语言、框架、数据库产品及版本留给实施计划评估；它们不能以“沿用旧项目”为选择理由。本文确定服务边界、数据责任和验收行为，不锁定未经验证的依赖组合。

## 5. 网站与小程序的信息架构

### 网站

- 桌面端侧栏固定六个默认社区，同时提供已加入社区、发现社区、收藏和最近浏览入口。
- 主区域是混合信息流，可按全部/已加入限定来源，并按最新/热门排序。这是两个独立维度，不是四种互斥内容类型。
- 顶部提供统一搜索、发布入口、通知和个人菜单。
- 每个社区提供概览信息流、资源、Wiki、成员与社区规则入口；负责人和版主有管理入口。
- 社区的独立 Wiki 提供词条详情、分类、搜索、新建、编辑、历史、差异与反向引用。
- 窄屏网站和小程序调整导航位置，保证固定社区仍有明确入口，不要求在手机上照搬桌面侧栏。

### 小程序

- 提供信息流、社区发现、发布、通知和个人区域；确切底部导航数量与分组由后续视觉稿确定。
- 核心业务范围与网站一致。Wiki 的浏览、新建、编辑、历史和回滚均在小程序中具备明确入口。
- 可视化编辑与 Markdown 是双端产品要求。实施前需要验证小程序编辑器的输入、公式与代码表现，不能默默降级成“只能跳到网站编辑”。如存在能力缺口，应给出具体演示并另行确定取舍。

游客看到全站公开内容与社区入口；“已加入”、云端收藏等个人功能在触发时引导登录，不用登录弹窗阻挡公开浏览。

## 6. 社区与内容模型

### 社区

社区包含名称、标识、简介、规则、头像/封面、负责人、版主、成员与启用的内容类型。每个社区必有独立 Wiki。六个默认社区是初始化数据与固定入口，平台管理员管理；普通社区版主不能删除平台默认入口。

申请包含名称、简介、主题范围和初始规则。平台批准后一次性创建社区、负责人角色、Wiki 空间与默认分类；驳回保留原因。负责人可邀请版主；受邀人接受后权限生效。

开发者建议：一个帖子、资源或词条拥有一个主要所属社区，可引用其他社区的内容；首版不提供“同一内容同时由多个社区共同管理”。加入社区是关注关系，不增加 Wiki 编辑的身份门槛；未加入但已登录的普通用户仍可编辑公开 Wiki，除非被限制。

### 内容类型

| 类型 | 必要行为 |
| --- | --- |
| 讨论/日常 | 图文正文、评论与回复、收藏、反馈/举报 |
| 问答 | 问题、回答、回答评论、提问者采纳；可以提议整理成 Wiki，但不自动发布词条 |
| 交易 | 出售/求购、价格、品类、成色、交付地点/方式、图片、公开留言、已出/完成标记 |
| 失物招领 | 寻物/招领、时间地点、描述图片、公开留言、已找回/已归还 |
| 搭子与活动 | 时间地点、说明、人数限制或不限、报名/取消、截止/取消/结束状态 |
| 树洞 | 正文、三种署名方式、回应、举报；匿名对外展示与账号责任分离 |
| 资源 | 标题、用途、类型、分类/标签、访问条件、链接或文件、说明、上传者、更新记录 |
| Wiki 更新事件 | 指向词条与版本的动态摘要，不复制一份无法同步的正文 |

默认社区按主题呈现适合的内容类型；自建社区可组合这些能力。具体字段必填性和类型开关由开发者在详细模型中定义，不应让每个社区从零配置才能使用。

开发者建议：信息流支持赞/踩，每个账号对同一项目只有一个当前投票；热门由反馈与时间衰减共同计算，具体公式留给实现。词条版本本身不做“按点赞确定正确性”的机制。同一词条的短时间连续修订合并为一条可展开的更新动态，避免信息流被修订记录占满。

## 7. 独立百科 Wiki

### 条目与引用

词条具有社区内唯一标识、标题、别名、摘要、正文、分类、当前版本和状态。标题可相同于其他社区的词条，链接始终包含社区上下文，避免指错页面。

支持站内词条链接、跨社区引用与反向链接。跨社区引用只建立导航关系，不共享正文与编辑权限。可搜索已有条目后插入链接；目标被归档时保留原引用并显示状态。首版不要求知识图谱可视化。

### 编辑与存储

- 普通登录用户可新建和编辑词条，自动获得稳定的贡献者昵称署名；树洞匿名方式不应用于 Wiki 历史。
- 可视化与 Markdown 使用同一受限内容模型，支持标题、列表、引用、链接、图片、表格、数学公式、代码块和词条引用。禁止直接执行作者提供的脚本。
- 每次发布生成不可变版本，记录作者、时间、变更说明、父版本、正文与引用。差异视图至少能定位文本变化，并标注附件/公式等非文本变化。
- 切换编辑模式不能静默丢失内容。无法无损表示的结构必须阻止切换并说明具体原因；基础支持范围应完成双向往返验证。
- 编辑器显示正在修改的基础版本。提交时基础版本已变更，服务端拒绝覆盖，提供最新版与本人修改，允许用户合并后重试。
- 普通修订保存即公开，不走常规内容的人工待审流程。事后检查、举报、版主保护和回滚处理异常修订。
- 回滚创建一个新的当前版本并记录操作者与来源版本，原有历史始终保留；链接和反向引用按新版本重建。

开发者建议：未被限制的登录用户可以发起回滚，按普通编辑记录并限流；版主可保护词条、暂停普通用户编辑，隐藏违规版本的公开正文，并保留治理审计。彻底删除、归档、改名等管理操作不能混同于普通编辑。

删除或隐藏当前版本引用的文件时，词条保留明确的附件不可用提示；不能因文件清理破坏历史结构。文件保留策略与备份恢复在实施计划中定义。

## 8. 账号、匿名和权限

核心身份是系统内部用户 ID。微信、邮箱、手机和用户名密码是同一用户的登录凭据。昵称、社区角色和树洞别名分别建模。

- 多种方式登录必须能够主动绑定到同一账号；绑定需要证明当前账号及新凭据的控制权。
- 不根据相同昵称推断同一用户，也不把“分别创建的两个账号”自动合并。微信网站端与小程序端的身份关联需通过实际配置验证；无法自动关联时提供明确绑定流程。
- 浏览不要求登录；发帖、评论、投票、加入社区、云端收藏、资源上传与 Wiki 编辑需要登录。公开资源下载默认不要求登录。
- 树洞固定昵称与普通个人主页隔离；每帖随机昵称只能在本帖内识别作者。公开 API、个人动态、通知、文件信息和版本引用均不能泄露匿名帖的普通作者身份。
- 后台保留树洞账号关联。开发者建议仅平台具备特定权限的治理人员可查看关联，社区版主只能处置内容及限制账号，身份查看行为记入审计。
- 资源和普通帖子可由发布者选择展示联系方式卡片；默认不展示。树洞不自动附加普通个人主页或联系方式。

角色为游客、普通用户、社区版主、社区负责人、平台管理员。所有社区权限均有社区作用域；负责人不能授予平台管理员权限。平台封禁和社区限制分别生效，受限用户不能通过 Wiki 或匿名身份绕过限制。

## 9. 自动检查与治理

普通帖子、评论、资源的状态流为：草稿 → 提交/自动检查 → 公开 / 人工待审 / 拒绝。检查不可用时保留处理中或待审，不把故障当作检查通过。作者可见状态、原因及修改入口。

内容编辑也须检查，新版本未通过时不能替换为公开版本；已公开的旧版本保持可见，除非被管理员单独下架。文件尚未通过检查时不能提供公开下载，即使说明文字已允许展示。

Wiki 普通编辑立即形成公开版本；其检查结果与普通内容队列分开处理。命中异常后由治理人员处置，紧急隐藏时保留版本和审计记录。词条保护用于处理持续破坏，不改变全站默认开放共建规则。

后台提供社区申请、普通内容待审、资源/文件状态、举报、Wiki 版本处置、账号限制、社区管理、配置与审计。社区负责人和版主只处理其社区可授权事项；平台处理跨社区和全站事项。

开发者建议：站内通知覆盖回复、回答采纳、活动变更、内容审核和社区申请结果；可以关闭非必要通知。它不是私信系统，也不默认给所有事件发短信或邮件。审核积压和失败任务可在后台查看与重试。

## 10. 新架构的边界

采用全新模块化后端，首版作为一个主要部署单元，后台任务独立调度；无需先拆成微服务。此为开发者建议，待设计确认。

| 模块 | 责任 |
| --- | --- |
| 身份 | 用户、登录凭据、会话、绑定与撤销、系统级限制 |
| 社区 | 社区申请、成员、规则、角色与权限 |
| 内容 | 类型化帖子、评论/回答、投票、收藏与状态 |
| Wiki | 空间、条目、修订、差异、回滚、分类和链接关系 |
| 资源与媒体 | 外链资源、文件元数据、上传授权、检查状态与下载授权 |
| 搜索与信息流 | 聚合可见内容、过滤与排序、更新事件；不作为正文真源 |
| 治理 | 自动检查衔接、审核、举报、处置与审计 |
| 活动 | 报名、容量与状态变化，防止重复报名和超额 |
| 通知与任务 | 通知、检查任务、索引更新、重试与备份任务记录 |

网站、小程序和管理界面均通过同一业务服务操作数据。关系型主存储保存业务记录和事务，文件使用独立对象存储或等效接口；搜索索引和信息流均可由主存储重建。

事务内提交业务修改和待处理事件，后台幂等处理检查、通知和索引更新。任务失败可重试且不重复发通知或制造版本。外部服务调用不持有长数据库事务。

已确认的功能必须具有实际业务接口与状态；开发演示可以使用明确标注的样例数据，但不能把模拟微信登录、验证码、文件下载或审核结果作为上线验收证据。

## 11. 旧项目保留与环境隔离

目前尚未制作或验证旧项目备份。实现前先盘点并备份源文件、必要的未纳入版本管理文件、数据库、上传文件和部署配置，记录时间、范围、校验与恢复方法。密钥备份单独保护，不能提交进代码库或公开报告。

新系统在独立目录/工作树中开发，采用独立数据库、存储路径、缓存前缀、端口和测试数据。新业务不读取或导入旧数据。不可直接清空原仓库、删除 `.data`、复用生产数据库后重置或覆盖原有线上服务。

## 12. 交付顺序与验收

以下是同一个完整首版的实现顺序，未将已确认功能移出首版：

1. 备份与隔离；验证网站/小程序的统一账号关联、双模式编辑器和文件上传等关键能力。
2. 统一身份、角色、六个默认社区、社区申请及治理后台骨架。
3. 百科 Wiki 的版本、冲突、差异、回滚、链接与双端编辑完整闭环。
4. 类型化内容、资源上传、评论与问答、交易/失物、活动报名、树洞身份。
5. 统一搜索、混合信息流、热门排序、收藏、通知与完整治理流程。
6. 双端视觉完善、跨端验收、备份恢复验证及部署准备。

最低验收场景：

- 游客在两端浏览六个默认社区、搜索资源与 Wiki，访问公开文件无需注册。
- 四种真实登录方式可用；绑定后两端使用同一用户，收藏和加入的社区一致。外部配置不足时必须列明阻塞项，不宣称完成上线。
- 用户申请社区，平台批准，负责人邀请版主；用户不可通过接口获得其他社区的管理权。
- 两个社区的同名词条各自维护；跨社区引用不混淆页面；分类、站内搜索和反向链接正确。
- 两人同时编辑同一词条，后提交者能发现冲突，第一人的修改不被覆盖；回滚生成新版本且历史完整。
- 公式、代码、表格、图片和词条链接在双模式往返及双端展示时保留含义；任何不支持的转换有明确提示。
- 普通内容通过自动检查后公开，疑似内容待审；失败任务可恢复；Wiki 普通修订不被错误放进常规人工待审。
- 树洞三种身份可选，公开请求与界面不泄露关联账号；治理权限与审计可验证。
- 二手标记完成、失物标记找回、问答采纳、活动取消/容量控制均有真实状态变化；公开留言和自选联系方式可用。
- 资源与 Wiki 更新可进入信息流，筛选和排序正确，搜索不会显示已下架正文。
- 新系统数据独立；旧项目备份和新系统备份各自可恢复，恢复记录不包含明文密钥。
