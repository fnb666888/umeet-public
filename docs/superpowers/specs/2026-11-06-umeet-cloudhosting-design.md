# Umeet 社区与 Wiki：当前统一设计

日期：2026-11-06（Asia/Shanghai）

状态：产品与技术访谈已汇总，并完成独立审阅；用户已确认共同理解，进入实施计划阶段，未开始正式产品实现或部署。

本文是当前方案。与早期 `2026-11-06-umeet-rebuild-design.md`、历史访谈条目冲突时，以本文和用户后续指示为准。逐题记录见 `2026-11-06-technical-ops-interview.md`。

## 1. 要做的产品

面向所有人的主题社区平台，校园为重点场景，但不限制学校身份或知识领域。组织方式类似 Reddit：首页提供社区导航与混合信息流；讨论中产生的长期知识进入各社区独立维护的百科 Wiki。

首页固定六个社区：树洞、交易、资源、问答、搭子与活动、校园日常。登录的正式用户可以申请新社区，平台审核后建立；申请人为负责人，可邀请版主。

这是全新产品和实现，不继承旧 UI 或应用架构。已有 HTML/CSS/JS Demo 暂时保持当前版本，作为视觉与交互方向参考；它不代表后端能力已接通。

## 2. 已选交付路线与取舍

| 决策 | 已选方案 | 未选或暂缓 |
| --- | --- | --- |
| 双端路线 | 网站与小程序分别定制，共用业务后端 | 共用一套跨端页面、拼装独立论坛/Wiki |
| 网站 | React + Next.js + TypeScript | Vue/Nuxt、纯静态 SPA 方案 |
| 小程序 | 微信原生小程序 + TypeScript | Taro 等适配框架 |
| 后端 | NestJS + TypeScript，模块化业务 | Django、提前拆微服务 |
| 数据库 | MySQL，业务与社区权限重新设计 | PostgreSQL；沿用旧表结构 |
| 部署 | 微信云托管，网站/API 两个服务 | 自管 Linux/Compose 与双地区部署先暂缓 |
| 认证 | NestJS统一管理认证、会话与业务账号，微信云托管 + MySQL | 用户2026-11-07明确不另接CloudBase托管认证 |
| Wiki 正文 | Markdown 为源格式，支持可视化/源码切换 | 编辑器 JSON 作为唯一正文源 |
| Wiki 协作 | 保存时检查基础版本，冲突人工合并 | 在线文档式实时共同编辑 |
| 搜索 | MySQL 全文与标题/标签/别名组合 | 独立 Meilisearch 等服务 |
| 任务 | API 内处理器 + MySQL 持久化任务 | 独立 Worker 服务、额外消息队列暂不引入 |
| 代码管理 | GitHub 私有单仓库，检查自动化，生产发布人工确认 | 首版多仓库、多套分散流水线 |

选择理由：保留完整的社区与 Wiki 产品能力，同时减少个人维护时的运行服务数量。两端共享的是接口、数据协议和业务规则，不直接共享界面组件。

MySQL 具体版本需在部署环境和备份工具兼容性验证后确定。8.4.x 仅是候选，未被用户确认为最终版本。数据库与文件均使用独立持久化服务，不放在应用容器本地作为唯一副本。

## 3. 用户、游客与注册

- 未登录也可浏览公开社区、资源和 Wiki，不用弹窗阻断阅读。
- 支持游客登录：可收藏、保留浏览记录和草稿；不能公开发帖、评论或修改 Wiki。
- 游客升级为正式账号后保留其数据。拥有匿名认证 UID 不等于拥有正式用户写入权限。
- 微信、邮箱验证码、手机验证码、用户名密码四种常见登录入口保留；支持常见注册方式，不强制所有人先通过同一个渠道注册。
- 用户2026-11-07已将认证改为NestJS后端统一管理，不再接CloudBase；必须验证微信网站/小程序身份、用户名密码注册、游客升级、账号绑定、邮件/短信发送与费用，不以假登录代替。
- NestJS/MySQL 保存自己的业务用户 ID，业务内容和权限引用该 ID，认证平台 UID、微信身份等通过映射关联。
- 默认不得仅因昵称相同自动合并账号。绑定或合并应证明所关联身份的控制权；具体交互在认证验证中完成。

密码、验证码、会话安全使用成熟组件，不自创加密算法。NestJS 负责认证和会话，MySQL 保存密码散列、身份映射、验证码状态及会话散列；不另接 CloudBase 托管认证。微信、邮件和短信仍需配置实际应用或发送服务。

## 4. 社区与信息流

桌面网站侧栏固定六个默认社区，并展示已加入的主题社区；手机网站和小程序采用适合窄屏的导航。主信息流混合帖子、资源与 Wiki 更新。

来源范围支持全部/已加入；排序支持最新/热门。资源和 Wiki 更新应指向其真实内容，不复制一份无法同步的正文。用户可以搜索、加入社区、收藏和查看自己的参与记录。

默认提案（待随本文一并确认）：每条帖子/资源有一个主要所属社区；跨社区通过引用连接。Wiki 每次修订都保留版本，但短时间连续修订可合并成一条动态摘要，避免占满信息流。帖子采用赞踩反馈，热门结合反馈与时间衰减；具体公式由实施者确定并测试。

## 5. 业务功能

| 功能 | 首版范围 |
| --- | --- |
| 日常讨论 | 图文、评论/回复、赞踩、收藏、举报 |
| 问答 | 提问、回答、采纳；好答案可整理成 Wiki，但不自动替代人工编辑 |
| 资源 | 校园信息、学习资料、工具/项目、生活与机会；外链和文件上传下载 |
| 交易 | 出售/求购、价格、成色、交付方式、留言、完成标记 |
| 失物 | 寻物/招领、时间地点、图片、留言、找回/归还状态 |
| 搭子/活动 | 发布、时间地点、报名/取消、容量与截止、取消/结束状态 |
| 树洞 | 普通昵称、固定树洞昵称、每帖随机昵称可选，后台均关联账号 |
| 沟通 | 公开留言 + 发布者自行选择展示的联系方式卡片 |

首版不增加私信、群聊、支付、担保订单或独立 App。文件在线预览未列为已选要求；上传下载不能以文件名占位或假链接作为正式实现。

上传额度已选：单文件 100 MB、单账号每日累计 200 MB，后台可调整；常用文档与 ZIP 需检查后才公开下载。站点接近存储或费用额度时暂停新上传。格式、请求类型、实际内容的检查分开设计，扩展名白名单不能替代完整检查。

## 6. 每社区独立百科 Wiki

每个社区维护自己的词条、分类、链接和版本历史。不同社区同名词条保持独立，跨社区链接不共享正文。词条按搜索、分类、链接和反向引用组织，不强制成为按顺序阅读的多级手册。

普通正式用户可新建、编辑词条，普通修改保存后立即生效，保留稳定的贡献者署名。词条应支持标题、列表、图片、表格、代码、公式和词条链接。

### Markdown 与编辑体验

网站默认可视化编辑，也可以切换 Markdown。两种模式遵循同一份内容规范，不能表示的结构必须明确提示，不静默丢失。编辑器具体产品留给实施阶段的兼容性验证，不凭库名承诺无损转换。

原生小程序也须具备 Wiki 浏览、新建、编辑、历史和回滚入口。不能认为网站编辑器可直接运行在小程序中；公式、表格、代码、图片和词条引用需在两端验证。不能未经确认把小程序编辑降级成只能跳网站。

### 保存、冲突与回滚

每次公开保存产生不可变版本，记录作者、时间、基础版本、Markdown、变更说明和引用。提交携带基础版本；如果别人已更新，拒绝静默覆盖，保留本次修改并提供最新版与冲突对照，人工合并后重试。

回滚建立新的当前版本，不删除原有历史；索引和引用按新版本更新。版本对照至少定位文本变化并标注附件等非文本变化，不把 Demo 的全文两栏展示等同正式差异实现。

默认提案：正式用户未受限时可回滚，按一次新编辑记录和限流；版主可保护词条、暂停编辑、隐藏违规版本并保留审计。是否加入社区不作为普通公开 Wiki 编辑的额外门槛。

## 7. 审核与管理权限

常规帖子、评论和资源通过自动检查后公开，疑似问题进入人工审核。检查失败或不可用时不假装通过，应显示处理中/待审及可恢复状态。文件未检查通过时不可公开下载。

Wiki 普通修订即时公开，事后检查、举报、版本处置和词条保护用于治理，不把普通修订悄悄改成人工先审。

角色：游客、正式用户、社区版主、社区负责人、平台管理员。社区管理权限必须包含社区作用域，平台封禁与社区限制分别生效。

已明确：只有所有者及指定平台管理员可以查看树洞账号关联，每次记录原因与审计日志。社区负责人和版主可审核、下架及限制违规账号，但不能自行揭示匿名作者账号身份。公开页面、API、动态、通知和文件信息不能绕过匿名隔离。

管理后台位于 Next.js 的 `/admin` 区域，独立开发界面，共用网站服务；管理页面与 NestJS API 都校验权限。后台覆盖社区申请、内容审核、举报、用户/角色、资源/文件、Wiki 版本处置、任务、配置和审计。

自动检查与文件检查的实际供应商、能力覆盖、授权和费用需验证；不能把关键词规则当作已实现所有安全检查，也不能默认所有附件均能通过同一微信接口检测。

## 8. 微信云托管运行结构

两个正式云托管服务：

1. 网站服务运行 Next.js，提供用户网站与 `/admin`。
2. API 服务运行 NestJS，提供网站和小程序共用的业务 API，并运行后台任务处理器。

正式网站和 API 各保留至少一个运行实例，减少缩容至零后的启动等待；测试环境允许休眠。具体 CPU/内存、扩容上限、计费及平台配额按实际环境验证，不能沿用先前虚拟机套餐报价。

服务无状态化，监听平台要求的端口。数据放 MySQL 与独立对象存储；文件上传下载授权不能把存储管理密钥放到客户端。多实例、重启与发布不能造成会话失效策略、任务或缓存内容相互矛盾。

后端按身份、社区、内容、Wiki、资源/媒体、活动、搜索、治理、任务/通知分模块组织。MySQL 是主数据源，搜索与信息流索引可重建，不另开每社区数据库。

## 9. 搜索与任务

搜索采用 MySQL 全文索引，配合标题、标签和别名查询，覆盖帖子、资源与 Wiki。中文、英文、混合查询、单字词条名均需测试；单字标题回退不意味着所有正文单字都可命中。相关性、停用词、索引及可见权限过滤由实施者验证；不增加独立搜索服务。

任务先持久化到 MySQL，API 内处理器领取执行。支持重启恢复、失败重试、防止重复业务副作用和后台状态查看。多个 API 实例需有任务抢占/租约与幂等机制，不能每个实例都无条件重复发送。

业务状态修改与任务事件可靠衔接，外部网络调用不持有长事务。常驻实例不等于任务必然成功；失败和积压需要可观测与告警。

## 10. 代码与发布管理

一个 GitHub 私有仓库分别管理网站、API、小程序和共享接口协议。提交后自动构建检查，先测试，生产发布由用户确认；网站/API 独立发布，不能因为修改一个页面就无条件同时替换全部服务。

构建产物与源代码版本关联，密钥放平台安全配置，不提交代码或打入公开客户端。代码和环境变更留记录。应用启动失败可回退旧镜像，数据库迁移需单独检查，不能盲目倒回表结构或覆盖数据。

仓库创建、真实密钥配置、云托管服务操作和生产切换尚未执行。本阶段只确认架构，不把一次选项回复当作已完成部署。

## 11. 旧系统直接替换

用户最新要求：**不需要旧数据，直接替换为新系统。** 因此不做数据迁移，不要求新旧服务并行，不将旧数据备份作为替换的强制前置条件。

新系统先完成可运行、测试和验收准备，再执行明确的旧入口替换；不能把尚未完成的新系统直接上传覆盖后再长期联调。实际替换服务、域名、小程序 API 与数据库对象需在部署阶段核对，不能删除不属于本项目的共享资源。

目标仍为两个正式服务。现有服务是否复用其服务名、正式域名如何接入、MySQL 复用实例中新建业务库还是新建实例，以实际环境和用户明确的替换范围确定。不要把“不迁移数据”理解成必须清空整个共享数据库实例。

## 12. 运维、预算与暂缓项

个人长期维护，无全天人工值班。告警首版只用邮件，即时通讯以后再定。外部探活配合 API、任务、备份、磁盘/容量与费用状态；故障持续约五分钟后通知，合并重复告警。

先前设定的试运行验证目标保留：1000 个注册账号、200 日活、20 人同时操作。数据测算基线为数据库 5 GB、资源文件 50 GB、资源文件下载 100 GB/月；均非已经验证的用量或承载保证。

费用目标原为 300 元/月，并允许与 500 元以内备选方案比较。改为微信云托管后按其实际计费重新核算，两个服务各一常驻实例的费用不可直接套用虚拟机报价。80% 额度告警，达到预设额度时限制文件与额外验证码等开销，尽量保留正文浏览和已有会话；应用配额不能保证供应商账单绝不超额。

此前 RPO 最多丢 1 小时、发现后 4 小时内恢复和每月恢复演练是目标。具体云数据库/文件备份能力、保留期、费用及恢复时长仍需验证，当前不承诺已满足。用户要求暂时不要扩大基础设施讨论，所以自管服务器、双地区部署/缓存、复制与精细备份费用留作后续，不作为首版当前的额外部署任务。

## 13. 首版验收与实施顺序

以下是同一个完整首版的实施顺序，不擅自移出已选功能：

1. 核验关键平台能力：认证/游客升级与双端绑定、MySQL/备份兼容性、双模式编辑器及小程序、文件上传与检查、两个云托管服务资源限制。
2. 新代码结构、统一业务账号与权限、默认社区、申请/邀请与后台。
3. Wiki 独立空间、Markdown 编辑、版本、冲突合并、差异、回滚和链接。
4. 各类帖子、资源上传、评论/问答、交易/失物、活动报名、树洞身份隔离。
5. 信息流、搜索、收藏、通知、审核与持久化任务；接口和双端验证。
6. 完整验收、发布准备与旧系统直接替换；之后按目标继续完善运维验证。

最低验收包括：

- 两端公开浏览不强制登录，游客不能越权写入，升级后收藏/草稿保留。
- 四种登录与常见注册、账号绑定、跨端身份实际可用，未支持的路径明确列为阻塞，不以 Demo 假登录代替。
- 六个默认社区、新社区申请、负责人邀请版主、作用域权限正确。
- 每社区独立 Wiki，同名词条不串页，双端内容含义一致，双模式切换无静默丢失。
- 并发修改不互相覆盖，回滚形成新版本，历史与引用可追踪。
- 发布检查与人工审核分流、匿名身份隔离、文件检查与授权、上传额度确实生效。
- 问答采纳、交易完成、失物归还、活动容量与状态有真实业务变化。
- 搜索覆盖各类型且不泄露不可见内容；任务重试不重复产生通知等副作用。
- 两服务分别构建、发布、健康检查；后台权限、邮件告警与回退流程可验证。
- 替换时旧业务数据不被迁入，新系统入口正确，不影响无关资源。

## 14. 开发者默认方案及待核实项

已随整体方案确认的默认规则：内容单一主要社区；赞踩与时间衰减排序；Wiki 更新动态合并；正式用户普通回滚按新修订处理；无需先加入社区才能编辑公开 Wiki；多身份合并需控制权证明；轻量站内业务通知（不是私信）。

实施者可决定并记录：具体依赖库和版本、编辑器产品、CSS/组件实现、ORM、API命名、数据库索引、差异算法、任务领取细节、具体限流参数、日志脱敏与保留、上传格式细节、部署脚本和测试工具。这些不要求用户继续逐个选择，必须符合已选体验、权限和验收。
